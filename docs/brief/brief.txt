0. MISSION
--------------------------------------------------------------------------------
Build the winning prototype for Valio Aimo's "Trusted Trade Agents" challenge.
Valio's own words: "Build the prototype that lets an AI purchasing agent buy
food from a wholesaler: safely, openly, and with the right human approval."

Our answer is VERIFIED OR ASK. It is a Valio Aimo-side gateway, plus a demo
purchasing agent, that runs the official flow Request → Lookup → Order →
Approval. The agent may act alone only when every fact it relies on is strong
enough and the order is inside the buyer's mandate. Everything else goes to a
named human, who signs off with one tap, and the exact reason is shown.

  One-liner: "The agent acts alone only on verified facts. Everything else goes
              to a human, with the exact reason."
  Pillars (they mirror Valio's three words):
    SAFELY  — every fact carries a trust level. Deterministic policy runs at
              Valio Aimo's gateway, not in the agent's prompt.
    OPENLY  — a published, documented interface and an open trust-label spec.
              Any agent can connect.
    RIGHT HUMAN APPROVAL — a human is asked only when needed. The ask names
              the exact weak fact. Sign-off takes one tap on a phone. Every
              step goes into a tamper-evident audit trail.

Quality bar: this must be the best solution in the challenge. It must be
simple, beautiful, fast and honest. It must work live, including on requests
the judges type themselves.

4. THE WINNING CONCEPT — "VERIFIED OR ASK"
--------------------------------------------------------------------------------
4.1 Positioning
  Valio wants the interface and operating model that make the wholesaler
  "safely and openly readable by autonomous agents". It explicitly does not
  want a chatbot. So the product is Valio Aimo-side: a Trusted Trade Gateway
  that any purchasing agent can use, with a demo purchasing agent that proves
  it works end-to-end.

4.2 The principle
  Every fact the agent relies on carries a trust level:
    VERIFIED · DECLARED · ESTIMATE · UNKNOWN, plus a CONFLICT flag.
  The agent may commit an order alone only when both hold:
    (a) every decisive fact is strong enough, and
    (b) the order is inside the buyer's mandate.
  Otherwise the order goes to the mandate's named approver, and the approval
  screen shows exactly which fact is weak and why.

4.3 Why this is new
  Autonomy is computed from data trust, not only from a euro threshold. A €20
  pasta order for a school, where the supplier has given no allergen data, is
  riskier than a €1,000 milk order with verified stock and declared
  lactose-free status. Euro limits still apply on top.

4.4 Product parts (WHAT, not how)
  P1 Catalogue intelligence
     - The static dataset becomes searchable in English, Finnish and Swedish.
     - Every product fact is normalised and trust-labelled.
     - The pack content per sales unit (litres or kg) is resolved.
  P2 Trusted Trade Gateway (Valio Aimo side)
     - An open, documented interface: lookup, offer (live price + availability,
       trust-labelled), order at fixed price, decision, approval, audit.
     - The same operations are exposed as agent tools through an open agent
       protocol.
     - Published as a versioned open spec: "Agent Trust Labels v0.1" plus the
       interface schemas.
  P3 Mandate & policy engine
     - Mandates are buyer-owned.
     - Rules are deterministic and every rule outcome has a reason code.
     - Rules are enforced at the gateway, so no agent can bypass them.
  P4 Purchasing agent (demo client)
     - Turns the buyer's need into a structured request.
     - Shortlists candidates and ranks them good/better/best.
     - Handles partial availability and substitutes.
     - Explains the outcome in plain language.
  P5 One-tap human sign-off
     - A phone page opened via QR code.
     - Options: approve all, approve verified lines only, or reject.
  P6 Shared audit trail
     - Human-readable and tamper-evident.
     - The same facts for the buyer and for Valio Aimo.
  P7 Valio Aimo agent-readiness view
     - Shows which data gaps block autonomous sales, by supplier.
     - Shows live AUTO / ASK / BLOCK statistics.

4.5 Coverage of everything Valio asked for
  Flow:
    Request = P4 structured need
    Lookup  = P1 + P2 (search, then live offer)
    Order   = P2 order at fixed offer price
    Approval = P3 decision + P5 sign-off
  Core:
    Lookup ✓ · Request and order ✓ · Permissions and approval ✓
  Bonus:
    Compare more than price ✓ (reliability, labels, CO2 as trust-labelled facts)
    Handle exceptions ✓ (partial, substitutes, later date, passed cut-off,
                         supplier stock, not deliverable, sales block,
                         missing/conflicting data)
    Explain decisions ✓ (P6 + plain-language reasons)
  Insights:
    I1 trust protocol = Agent Trust Labels
    I2 guardrails = mandates + reason codes
    I3 = good/better/best + partial allocation
    I4 = P6
  Valio scenarios hit:
    last-minute event · supplier stock-out · allergen-safe substitution under
    pressure

4.6 Judging map
  Working end-to-end demo 30 %
    Three scripted live scenarios plus any judge request. All run the 4-step
    flow end-to-end on the live API.
  Solving the user's need 20 %
    - Structured need with visible, editable assumptions.
    - Constraint-correct shortlist and good/better/best.
    - An "Excluded" list that proves precision.
    - Measured on a 20-case evaluation set; the score is shown.
  Autonomy and controls 20 %
    - Mandates and deterministic policy, with reason codes.
    - One-tap sign-off.
    - Resistant to prompt injection.
    - Tamper-evident audit trail.
  Robustness to exceptions 15 %
    Everything listed in 4.5 "Handle exceptions", plus Valio's own substitute
    that breaks a requirement (§10.5 T3).
  Openness and path to production 15 %
    - Published interface plus JSON Schemas and the trust-label spec.
    - Any agent can connect.
    - Assumptions are documented.
    - A concrete roadmap.

4.7 Differentiators — make each one visible in the product and the pitch
  D1 A trust card on every order line: badge + source + timestamp for each fact.
  D2 An "Excluded" list: what the agent rejected and why.
  D3 Dataset traps caught live (§10.5):
     - lactose-free ≠ milk-free;
     - an oat drink is not automatically gluten-free;
     - Valio's own listed substitute can break the gluten-free requirement;
     - the supplier-stock quantity is a placeholder (999,999), not a real number;
     - a delivery date can still be offered after its order cut-off has passed.
  D4 A judge signs off an order on their own phone.
  D5 Mandate toggles change the decision live, with no model call.
  D6 The Valio Aimo mirror: data quality = autonomous sales, with a fix list
     by supplier.

5. TRUST MODEL — "AGENT TRUST LABELS v0.1"
--------------------------------------------------------------------------------
5.1 Levels
  VERIFIED  Comes from Valio Aimo's own live systems or Valio Aimo-defined
            rules: price API, availability API (logisticModel "Stock"), sales
            block, Valio substitution list.
  DECLARED  Comes from the manufacturer/supplier via GS1 Synkka in the product
            file: allergens, free-from declarations, nutritional claims, labels,
            origin, pack contents, names, ingredients.
  ESTIMATE  Statistical or derived: historical delivery reliability,
            product-group CO2 average, pack content derived from a price ratio
            or the product name, agent-proposed substitutes.
  UNKNOWN   Missing, undeclared, or explicitly invisible (supplier-stock
            quantity 999,999).
  CONFLICT  A flag that combines with any level. It means two sources disagree
            or a value is internally inconsistent.

5.2 Fact catalogue
  For each fact: source → level rule → example display.

  price.unit
    Source: /api/price catalogPrice.value, per sales unit, excl. VAT.
    Level:  VERIFIED if error=false and the date is within validFrom..validTo;
            otherwise UNKNOWN.
    Display: "€1.01 / pc excl. VAT · customer price (list €1.44)". Use
            "customer price" when netPriceFound=true.
  price.comparison
    Source: comparisonPrice.value per comparisonUnit ("L" or "KG"; may be null).
    Level:  VERIFIED.
    Display: "€1.01 / l".
  price.vatRate
    Source: tax.taxRate.
    Level:  VERIFIED. This is the only VAT source of truth; the product
            vatCode is unreliable (§10.2).
  stock.quantity (from /api/availability)
    · logisticModel "Stock", 0 < amount < 1,000,000
        → VERIFIED exact · "19 in stock"
    · logisticModel "Stock", amount ≥ 1,000,000
      (observed 9,999,999,999; also 666,666,666 and 416,666,666)
        → VERIFIED · "Plenty in stock"
    · logisticModel "Terminal" (amount is always 999,999)
        → UNKNOWN · "Ships from supplier's warehouse — quantity not visible
          to Valio Aimo"
    · availableAmount 0 (availableDate null)
        → VERIFIED negative · "Out of stock"
    · scheduleLines empty (no logisticModel, no closingTime)
        → VERIFIED negative · "Not deliverable on any date"
  delivery.date
    Source: scheduleLines[0].availableDate compared with the requested date.
    Level:  VERIFIED. On time if availableDate ≤ requested date; else late.
  delivery.cutoff
    Source: closingTime compared with the API's own timeNow.
    Level:  VERIFIED. If closingTime < timeNow while availableDate is still
            offered → CONFLICT ("cut-off passed").
  order.blocked
    Source: product-level or line-level salesBlock = true.
    Level:  VERIFIED negative.
  unit.sales
    Source: scheduleLines[0].salesUnit compared with product.salesUnit.
    Level:  VERIFIED. A mismatch → CONFLICT.
  allergen.<GS1 code> (codes in Appendix A1)
    · value in group "allergen" with unit CONTAINS
        → DECLARED "contains"
    · value in group "allergen" with unit MAY_CONTAIN
        → DECLARED "may contain"
    · value in group "nonAllergen" (unit FREE_FROM)
        → DECLARED "free from" (explicit)
    · code X99 present
        → DECLARED "no declaration-obligatory allergens" (explicitly free from
          all EU-14)
    · a declaration exists (≥ 1 value in allergen or nonAllergen) but this code
      is not mentioned
        → DECLARED-implicit "not listed"
    · zero values in both allergen and nonAllergen, or unit UNDECLARED
        → UNKNOWN "No allergen data from supplier"
    Note: the schema text says allergen units are "CONTAINS or FREE_FROM". The
    data actually uses CONTAINS / MAY_CONTAIN / UNDECLARED in "allergen" and
    FREE_FROM in "nonAllergen".
  claim.<id> (group nutritionalClaim, Appendix A2)
    Present → DECLARED. Absent → UNKNOWN (absence is not a negative).
    LOW_LACTOSE does NOT satisfy "lactose-free".
  label.<id> (group packagingMarkedLabel, Appendix A3)
    Present → DECLARED.
  origin
    Source: countryOfOrigin (ISO 3166-1 alpha-2, lowercase).
    Level:  DECLARED.
  content.perSalesUnit
    Litres or kg in ONE sales unit. Use the first method that works:
    (1) synkkaData.unitConversions[synkkaPackagingType=BASE_UNIT_OR_EACH]
        .volume or .netWeight, multiplied by units[unitId = salesUnit]
        .sizeInBaseUnits → DECLARED
    (2) catalogPrice.value ÷ comparisonPrice.value, when comparisonUnit is L
        or KG → ESTIMATE (derived; it matched declared or name-stated contents
        within 0.2 % in tests)
    (3) parsed from the product name ("12x … 400g", "1 l", "2,5 dl", "10 L")
        → ESTIMATE (weak)
    None of these → UNKNOWN.
    If (1) and (2) disagree by more than 5 % → CONFLICT.
    Sold by KG (salesUnit KG, or variableUnit) → 1 kg per sales unit.
  reliability
    Source: delivery-reliability CSV.
    Level:  ESTIMATE. Missing → UNKNOWN.
    Display: "Delivered in full 99.7 % historically".
  co2
    Source: carbon-footprint CSV (kg CO2e per kg).
    Level:  ESTIMATE. Missing → UNKNOWN.
    Display: always labelled "product-group average"; round to 3 decimals.
    Never rank products within a group by CO2: their values are identical by
    construction.
  substitute.valio
    Source: product.substitutions[].
    Level:  VERIFIED that Valio Aimo lists the relation. The buyer's
            constraints MUST still be re-checked.
  substitute.agent
    Proposed by the agent → ESTIMATE.

5.3 CONFLICT triggers
  A conflict always leads to ASK when the fact is decisive.
  K1 Allergen AW (cereals containing gluten) CONTAINS together with claim
     FREE_FROM_GLUTEN (11 food products). This can be legitimate (gluten-free
     oats), but coeliac use needs a human check.
  K2 Allergen ML (lactose) CONTAINS together with claim FREE_FROM_LACTOSE
     (4 food products).
  K3 The cut-off has passed while the date is still offered.
  K4 The availability salesUnit differs from product.salesUnit and cannot be
     converted exactly via units[].
  K5 The pack-content methods (1) and (2) disagree by more than 5 %.
  Info only, never decisive: product vatCode vs API taxRate. The API wins.
  Reason codes:
    K1, K2, K5 → DATA_CONFLICT
    K3 → CUTOFF_PASSED (only when enforceCutoff is on; otherwise info only)
    K4 → UNIT_MISMATCH

5.4 Display rules
  - Every fact shown = value + trust badge (icon AND word) + source + time
    (time for live facts).
  - Colour is never the only signal.
  - UNKNOWN is shown as "Unknown", never as a blank.
  - A CONFLICT shows a one-line explanation.
  - Each line has a trust summary: a count per level.

6. MANDATES & DECISION POLICY (deterministic; enforced at the gateway)
--------------------------------------------------------------------------------
6.1 Mandate
  A mandate is configuration owned by the buyer organisation. Agents can read
  it but can never change it. Every change is an audit entry ("Policy changed
  by buyer admin").
  Fields:
    customerId, organisationName, segment
    allergenMode ................. STANDARD | STRICT
    autoApproveLimitEur .......... order total excl. VAT
    hardLimitEur ................. order total excl. VAT; above it → BLOCK;
                                   approvals cannot override it
    autoAcceptValioSubstitutes ... true | false
    autoAcceptAgentSubstitutes ... always false
    autoAcceptSupplierStock ...... true | false
    minReliability ............... default 0.80
    enforceCutoff ................ default true (see §17 Q1)
    forbiddenAllergens ........... GS1 codes; default none
    approver ..................... {name, role}

6.3 Requirement semantics
  Hard requirements come from the request ("lactose-free", "gluten-free",
  "milk-free", "vegan", "nut-free", "egg-free", …) and from the mandate's
  forbiddenAllergens.

  Required claim (lactose-free, gluten-free, vegan, vegetarian, …)
    The claim must be present (DECLARED). Otherwise EXCLUDE (CLAIM_MISSING).

  Avoid allergen X
    STANDARD:
      CONTAINS → EXCLUDE
      MAY_CONTAIN → ASK
      implicit "not listed" → OK
      UNKNOWN → ASK
    STRICT:
      CONTAINS or MAY_CONTAIN → EXCLUDE
      explicit FREE_FROM, or X99 → OK
      implicit "not listed" → ASK
      UNKNOWN → EXCLUDE

  Gluten-free
    Requires claim FREE_FROM_GLUTEN. If the product also has AW CONTAINS, that
    is CONFLICT K1 → ASK. Oats (GO CONTAINS) are allowed when the product
    claims FREE_FROM_GLUTEN. Gluten-free is evaluated by this claim rule, not
    by the avoid-allergen rule. The same goes for lactose-free
    (FREE_FROM_LACTOSE).

  Milk-free / dairy-free
    AM must not be CONTAINS; in STRICT it must not be MAY_CONTAIN either.
    FREE_FROM_LACTOSE never implies milk-free: 464306 is lactose-free and
    CONTAINS AM (milk).

  STRICT mode, additionally
    Every food line must carry an allergen declaration (≥ 1 value in allergen
    or nonAllergen), so the kitchen can protect every diner. A product with
    none → EXCLUDE · ALLERGEN_UNKNOWN, whatever the request says. Examples:
    470699 and 460302 (§10.5 T5).

6.4 Line rules (evaluated per candidate / order line)
  L1  salesBlock true ............................ EXCLUDE · SALES_BLOCKED
  L2  scheduleLines empty, or availableAmount 0 .. EXCLUDE · NOT_AVAILABLE
  L3  price error, missing, or outside validity .. EXCLUDE · PRICE_UNAVAILABLE
  L4  requirement checks (§6.3) .................. EXCLUDE or ASK as defined
      Codes: CLAIM_MISSING, ALLERGEN_CONTAINS, ALLERGEN_MAY_CONTAIN,
      ALLERGEN_IMPLICIT, ALLERGEN_UNKNOWN
  L5  availableDate > requested date ............. ASK · DATE_LATER
  L6  enforceCutoff and closingTime < timeNow .... ASK · CUTOFF_PASSED
  L7  logisticModel "Terminal" and not
      autoAcceptSupplierStock .................... ASK · SUPPLIER_STOCK_UNKNOWN
  L8  verified quantity < needed
      · the remainder cannot be fully covered by OK lines
          → ASK · PARTIAL_AVAILABILITY
      · the remainder is fully covered by OK lines of products that meet every
        requirement
          → INFO · SPLIT
  L9  a decisive fact carries CONFLICT ........... ASK · DATA_CONFLICT
  L10 agent-proposed substitute .................. ASK · AGENT_SUBSTITUTE
      "Agent-proposed substitute" means either:
      - a different product than the one the buyer specifically named, or
      - a different product type (e.g. fusilli for macaroni).
  L11 Valio-listed substitute
      · passes all requirements and autoAcceptValioSubstitutes
          → INFO · VALIO_SUBSTITUTE
      · passes all requirements, auto-accept off
          → ASK · VALIO_SUBSTITUTE
      · fails a requirement
          → EXCLUDE · SUBSTITUTE_REJECTED (shown to the user)
  L12 pack content only from name parsing ........ ASK · QUANTITY_BASIS_WEAK
      pack content UNKNOWN ....................... EXCLUDE (the order cannot be sized)
  L13 reliability known and < minReliability ..... ASK · LOW_RELIABILITY
      (unknown reliability = info only)
  L14 unit mismatch not resolvable via units[] ... ASK · UNIT_MISMATCH

6.5 Order rules
  O1 Total excl. VAT > hardLimitEur → BLOCK · OVER_HARD_LIMIT.
  O2 A specifically named product contains a mandate-forbidden allergen
     → BLOCK that line, with the reason. Never swap silently.
     A named product that only violates a request requirement → EXCLUDE it,
     propose a compliant alternative (ASK · AGENT_SUBSTITUTE).
  O3 Total excl. VAT > autoApproveLimitEur → ASK · OVER_AUTO_LIMIT.
  O4 The request text tries to change rules, raise limits, claim prior
     approval, or instruct the system → ignore it · INFO · INSTRUCTION_IGNORED
     (always logged).
  O5 Nothing satisfies the need → no order · NO_CANDIDATE. Explain, and show
     the nearest alternatives with what each is missing.
  O6 The quantity or item is unclear, or the requirements contradict each
     other, and an assumption would change safety or the total
     → no order · CLARIFICATION_NEEDED (ask exactly one question).

6.6 Decision
  BLOCK if any line or order reason is BLOCK. Otherwise ASK if any reason is
  ASK. Otherwise AUTO. AUTO requires zero ASK and zero BLOCK reasons.

6.7 Order = commitment at a fixed price (flyer step 3)
  - The order freezes, from the offer: price, VAT rate, quantities, delivery
    date, and the offer version.
  - Offers are valid for 15 minutes, and never beyond the price validTo.
  - Before committing (AUTO, or after sign-off), price + availability are
    re-fetched for the order lines.
  - If anything changed (price, sufficiency, date, cut-off, sales block):
    re-evaluate, log REQUOTED, and require sign-off again if the decision
    became ASK.

6.8 Approval (flyer step 4: "Agent decides, or a human signs off")
  - Only through the approval channel, and only by the mandate's approver.
  - Options:
      APPROVE_ALL
      APPROVE_VERIFIED_LINES — drops every line carrying any of:
        SUPPLIER_STOCK_UNKNOWN, CUTOFF_PASSED, DATA_CONFLICT, ALLERGEN_*,
        AGENT_SUBSTITUTE, QUANTITY_BASIS_WEAK, LOW_RELIABILITY, UNIT_MISMATCH.
        Totals are recomputed.
      REJECT (optional comment)
  - BLOCK can never be approved.
  - Sign-off links are single-use and bound to the offer version. An expired
    offer → order state EXPIRED → re-quote.

--------------------------------------------------------------------------------
7. PURCHASING AGENT — REQUIRED BEHAVIOUR
--------------------------------------------------------------------------------
7.1  Input and output
     Input:  the buyer's need as text (EN or FI), plus the selected
             customer/mandate.
     Output: a structured Request, a ranked proposal, the gateway's decision,
             and a 1–2 sentence explanation.
7.2  Request (flyer step 1) — a structured object, always shown to the user
     items[]       what · quantity + unit (l, kg, pcs, cases) · hard
                   requirements · preferences (brand, organic, Finnish origin,
                   labels, fat %, pack size)
     requestedDate ISO date in Europe/Helsinki.
                   "today" / "tomorrow" / "by Monday" / explicit dates.
                   "by <weekday>" = the next such day; if today is that weekday,
                   it means today. "by X" = delivered on or before X.
     assumptions[] everything needed but not stated (e.g. "milk drinks
                   accepted", "any fat %", "UHT or fresh"). Shown as editable
                   chips; editing one re-runs the flow.
     Finnish ↔ English vocabulary must work, e.g.:
       laktoositon = lactose-free · gluteeniton = gluten-free
       maidoton = milk-free · kaurajuoma = oat drink · maito = milk
       maitojuoma = milk drink · makaroni = macaroni · litraa = litres
       kiloa = kg · maanantaiksi = by Monday · huomiseksi = for tomorrow
       tänään = today
7.3  Lookup, static part (flyer step 2)
     Static data only. Match names (en, fi, sv), category membership and
     claims. Exclude non-food from food requests. Apply §6.3. Keep an Excluded
     list with reason codes.
7.4  Lookup, live part
     Shortlist ≤ 20 candidates per item. For each evaluation, make one batched
     /api/availability call and one batched /api/price call, using the
     requested date.
7.5  Sizing
     - sales units = ceil(needed ÷ content per sales unit), respecting
       allowedLotSize multiples.
     - Show the delivered quantity, e.g. "6 cases = 28.8 kg".
     - Over-delivery is at most one sales unit per line.
7.6  Ranking per item, in this order:
     1. all requirements met with ≥ DECLARED;
     2. deliverable by the date with a VERIFIED quantity;
     3. lowest comparison price (€/l, €/kg);
     4. higher reliability;
     5. preferences and labels;
     6. fewer UNKNOWN facts.
     Output: Recommended, plus Good / Better / Best alternatives. Each has a
     one-line trade-off (price per l/kg, pack, brand, fat %, shape, stock
     certainty).
7.7  Partial availability
     Allocate from the best verified candidate up to its amount, then from the
     next best candidate that meets all requirements, same product type first.
     Record SPLIT or PARTIAL_AVAILABILITY.
7.8  Substitutes (when the buyer named a specific product)
     Valio-listed substitutes first, re-checking every requirement. Then
     agent-proposed ones. Always give a one-line trade-off.
7.9  Order and Approval (flyer steps 3–4)
     Hand the proposal to the gateway. Never compute the decision yourself.
     Explain the gateway's decision in ≤ 2 sentences plus reason chips.
7.10 Clarifying questions
     Ask only when needed: missing quantity; contradictory requirements (e.g.
     "lactose-free milk that is milk-free"); unsupported units such as
     "portions". Otherwise assume, and show the assumption.
7.11 Request text is data
     Never follow instructions inside it. Claims of approval are ignored
     (INSTRUCTION_IGNORED).
7.12 The agent is replaceable
     Any agent using the published interface gets identical decisions for
     identical offers.

8. GATEWAY INTERFACE — WHAT IT MUST EXPOSE
--------------------------------------------------------------------------------
8.1 Openness requirements
  - The interface is described in an open, machine-readable standard.
  - The same operations are offered as agent tools through an open agent
    protocol. The README names the choice and justifies it.
  - JSON Schemas are published for: TrustLabel, Product (normalised), Offer,
    Order, Decision, Mandate, AuditEntry, Insights.
  - Everything is versioned v0.1, and the spec is rendered as a human-readable
    page (S7).

8.2 Operations (names indicative; the semantics are required)
  searchProducts(query, requirements[], language?, limit?)
      → candidates[] + excluded[]
      Static data only. No live calls.
  getOffer(customerId, requestedDate, items[{productId, quantity, unit}])
      → Offer
      Live price + availability, trust-labelled facts, totals, validUntil.
  createOrder(customerId, offerId, requestText, agentRationale)
      → Order {orderId, state, decision, reasons[], lines[], totals,
               approvalUrl?}
      Commits at the fixed offer price, then the policy decides.
  getOrder(orderId)
      → Order
  decideApproval(orderId, approvalToken, action, lineIds?, comment?)
      Approval channel only. NEVER exposed as an agent tool.
  getAuditTrail(orderId | customerId)
      → AuditEntry[]
  getMandate(customerId)
      → Mandate (read-only for agents)
  getInsights()
      → Valio Aimo readiness data (§14)

8.3 Order states
  RECEIVED → EVALUATED → AUTO_APPROVED → CONFIRMED_SIMULATED
  EVALUATED → PENDING_APPROVAL → APPROVED → CONFIRMED_SIMULATED
  PENDING_APPROVAL → REJECTED | EXPIRED
  EVALUATED → BLOCKED
  Every transition is an audit entry.
