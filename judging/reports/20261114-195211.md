## Verdicts

- **commercial**: The most trustworthy purchasing gateway I tested: real mandate logic, split-order detection, allergen-safe substitutes and an open spec. It loses points for all-or-nothing multi-line orders and patchy Finnish.
- **online-sales**: The clearest approver experience I saw: honest exceptions, allergen-safe, and fast to approve on a phone. But the open API can't commit an order for a real external agent yet.
- **tech-governance**: The best guardrails and provenance model on the table, with rules enforced on the server and resistant to manipulation, but an outside agent can't complete an order through the API without browser cookies, and a coeliac context slipped through in a school kitchen.

## Bugs seen by judges

- **[medium] Finnish partitive product noun not matched** (commercial): School kitchen: 'Sairaalan keittiö: 15 kg kananmunatonta majoneesia huomiseksi, potilailla munaallergia' → expected: Search mayonnaise with no-egg requirement; actual: Item 'majoneesia', 'No eligible products matched', no candidates evaluated
- **[medium] Unknown claim code silently excludes all products** (commercial): POST v0.1/products/search {query:'whipping cream', requirements:[{kind:'CLAIM',code:'LACTOSE_FREE'}]} → expected: 422 with valid codes (FREE_FROM_LACTOSE); actual: 200 with 0 candidates; all lactose-free creams excluded as CLAIM_MISSING
- **[medium] Offer not found when creating proposal from separate HTTP call** (commercial): POST v0.1/offers then POST v0.1/proposals with the returned offerId/version → expected: Proposal created and decided; actual: 404 'Unknown offer OF-... v1'

- **[low] Approve buttons remain after approval** (online-sales): Approve a proposal on /approver → expected: Detail shows Approved state, no action buttons; actual: Queue row says Approved but the detail still shows 'Approve €506.16' / 'Reject'

## Strengths

- Deterministic AUTO/ASK/BLOCK gateway against a buyer-owned mandate, with plain-language reasons (commercial)
- Same-day order aggregation prevents splitting orders to dodge the auto-approve limit (commercial)
- Fact-level provenance (Verified/Declared/Estimate/Unknown) with sources and an open spec (commercial)
- Allergen safety: substitutes must satisfy the original hard requirements; unknown allergen data is excluded, never waived (commercial)
- Phone-friendly, version-bound, single-use approval with a live re-check (commercial)
- Valio-side readiness view turns data gaps into a commercial fix list (commercial)
- Every AUTO/ASK/BLOCK decision comes with plain-language reasons an approver can act on in seconds, including 'Approving means X instead of Y' (online-sales)
- Strict allergen handling in Finnish: milk-free + gluten-free enforced, the substitute's claims sourced, and the form change escalated (online-sales)
- Honest exception handling: cut-off passed, partial stock, split orders and rejected supplier substitutes are all explained (online-sales)
- Mobile approver page is genuinely usable: exact lines, totals, a large approve/reject and a comment for the audit (online-sales)
- Facts carry provenance (Verified/Declared/Estimate/Unknown, source field, retrieval time) (online-sales)
- Clearly not a chatbot: a structured request with editable assumption chips (online-sales)
- Rules for auto-confirm, human approval and block enforced on the server, with strict schemas; approval never exposed to the agent (tech-governance)
- Every fact is labelled VERIFIED/DECLARED/ESTIMATE/UNKNOWN with source system, field and timestamp, plus a published spec (tech-governance)
- Manipulation attempts detected and logged in EN and FI (tech-governance)
- Partial-availability split, date retry and exclusion reasons shown openly (tech-governance)
- OpenAPI 3.1 + MCP + readiness view on Valio's catalogue data quality (tech-governance)
